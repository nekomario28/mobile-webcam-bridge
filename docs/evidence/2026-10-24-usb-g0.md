# USB path: G0 measured, G0.5 intermittent (2026-10-24)

Device: Sony XQ-GE44 (Android 15), APK 0.2.0, host debug build. No reboots: the phone was
reset between attempts with `adb shell svc usb resetUsbPort` and an app `force-stop`.

## G0 — AOA capability and transition: PASS

```
before: Bus 001 Device 033: ID 0fce:320d Sony Ericsson Mobile Communications AB XQ-GE44
after:  Bus 001 Device 034: ID 18d1:2d01 Google Inc. Android Open Accessory device (accessory + ADB)
```

`0x2d01` is accessory + adb, which is what to expect while USB debugging is on; the gate's
`0x2d00` assumes debugging is off. The probe prints the post-transition identity itself
(`device after the transition: 1:18d1:2d01 (accessory: true)`), so the transition is
evidence of the run, not of a separate `lsusb`.

## G0.5 — framed bulk smoke test: passes at 50, intermittent at larger counts

`mobile-webcam --usb-probe --frames 50 --budget-ms 8000`:

| attempt | result |
|---|---|
| 1 | **PASS** — sent 50, echoed 50, 0 mismatch, 0 timeout, 2 skipped, rtt us min 72 avg 91 **p50 80** p95 113 max 236 |
| 2 | FAIL — `expected authorization outcome before capabilities/media` |
| 3 | **PASS** — rtt us min 70 avg 88 p50 85 p95 113 max 148 |

Two of three. The 1000-round-trip count the gate asks for did not complete in any attempt:
each run ended either at `incomplete frame deadline expired` (the reader received a header
whose payload never finished inside the 5 s frame lifetime) or at the failure above.

**Not claimed:** a cross-device latency figure (the gate forbids it) or a G0.5 pass. What
is claimed is that a driver now exists, that it passes at 50 round trips, and that the
failures above are reproducible with the commands in this file.

## Three host defects the gate found (all fixed here)

1. **The stream was not aligned when the host opened the accessory.** The accessory
   endpoint holds whatever the phone wrote before this host connected, and AOA reports no
   disconnect, so a new host process starts reading in the middle of a frame. Measured with
   `--usb-dump`: `66 bytes` (a payload) then `24 bytes` (a header) repeating — every header
   read as garbage, so the reader could never complete a frame. `Usb::connect` now calls
   `align_stream()`, which drops transfers that do not begin with `AMB1` and hands the first
   real header to the reader through a small `pending` buffer (dropping it would lose a live
   frame — the first implementation did exactly that and the app, which sends one challenge
   per session, then had nothing left to sign).
2. **Stale bytes made the host sign a challenge the phone had already replaced**, which the
   phone answers `BAD_SIGNATURE` — a misleading "your key is wrong" for a framing problem.
3. **Frames the probe is not waiting for were read as replies.** The phone advertises its
   capabilities right after authorizing, and the first version counted that as the PONG of
   every exchange (`sequence-mismatch 20`). The probe now skips non-PONG frames and reports
   how many it skipped, as the shipping session does.

## Diagnostics added (kept: they are how the above was found)

| command | shows |
|---|---|
| `--usb-probe [--frames N] [--budget-ms N]` | G0/G0.5: transition, authorization, then N PING/PONG with sequence and payload checked, RTT percentiles, exit 0/1/2 |
| `--usb-dump <seconds>` | the raw transfers the phone sends, unparsed |
| `--usb-frames <seconds>` | the frames the real reader parses, or the error it hits |
| `AMB_USB_TRACE=1`, `AMB_AUTH_TRACE=1` | endpoint/packet sizes, and the transport/binding/nonce/label a proof was built from |

## The second failure is a phone-side protocol violation, not a host bug

`protocol/client-authorization-v2.md` says it outright: *"Repeated Pending,
media/capabilities before Authorized or another proof on the same challenge is a protocol
error."* The host implements exactly that — `client_auth::exchange` refuses any frame that
is not `CLIENT_AUTH_RESULT` while it waits for the outcome — and it is **right** to: that
rule is what stops a peer from feeding control or media traffic to a host that has not been
authorized yet. The measured failure (`expected authorization outcome before
capabilities/media`, in 1 of 3 attempts) is therefore the **phone sending capabilities
before its authorization result**, i.e. a violation of its own half of the protocol, not a
host that is too strict.

The disposition is consequently: **do not relax the host**. Recording it here is the
finding; an app-side change is what would close it, and it is the same area as the
one-challenge-per-session behaviour above (both are the app's session lifecycle around a
host that reconnects).

## Why the count is not met yet

Both failure modes point at the phone's session lifecycle rather than at the link: the app
sends exactly one challenge per accessory session and then waits, and it starts a new
session (a rediscovery cycle) whenever one ends — so a host that connects while the app is
between sessions, or while a session's writer is mid-frame, sees either an out-of-order
capability frame or a frame whose payload never arrives. The app also needs **user approval
of the USB accessory** on attach, which makes each attempt cost a tap; that friction is why
this run is short and why the remaining work should land as an app-side fix, tested without
the accessory where possible.

## Instrument lesson worth keeping

`--usb-frames` and `--usb-probe` cannot be run back to back: the first consumes the app's
single challenge, and the second then waits out its whole budget for one that will not be
re-sent. A diagnostic that changes the state it measures has to be run in its own attempt.

## Two more defects found while closing this out (2026-10-24)

**A failed USB attempt leaves the phone in accessory mode, and nothing said so.** AOA has no
"leave accessory mode" request, so after a failure the phone stays rolled into the accessory
with nothing reading it: the app waits for a PC that will never come, and the *next* attempt
finds a session that will not start a new exchange — which is what made every retry in this
session cost a reset. The host's USB failure path now names it (`video.rs`: *"The phone is
still in USB accessory mode; unplug and replug the cable before trying again"*), and the
reset that works without touching the cable is `adb shell svc usb resetUsbPort` — that is how
this session got its clean attempts, no reboots.

**The accessory description we send is `"Low-latency Android to Linux media bridge"`**
(`usb.rs`, one of the six strings `specs/rust-host-rewrite/contracts.md` pins as the
transport identity, with "do not rebrand"). That string is what the phone's approval dialog
shows the user, so it is the thing a person reads every time they are asked to allow the
accessory — and it advertises a property (low latency) this path does not claim anywhere
else. Changing it is a spec decision, not a code cleanup: either the spec keeps the string
and the dialog keeps saying it, or both move together.

## Second device session (2026-10-24, later): what the new code does on hardware

The phone came back, the new APK was installed (`-r -g`, same debug signer, dex confirmed to
carry `TYPE_HOST_HELLO` / `onHostHello` / `closeAndAwait`), and adb drove the run. No reboots:
`adb shell svc usb resetUsbPort` plus an app force-stop between attempts.

**Verified on hardware**

- **Alignment works.** With a fresh app process the reader parses the phone's frames:
  `frame kind=0x0a seq=1 len=66` — the authorization challenge, repeatedly. Before
  `align_stream` this run could not complete a single frame.
- **`HOST_HELLO` fires and the host retries.** An attempt against a spent session printed
  `retrying after a host hello: deadline expired`, i.e. the host recognised the shape and sent
  the reset frame.

**Still failing, and where**

Two failures remain in the phase *after* authorization — the reader cannot sustain the
session long enough for 1000 round trips:

| error | what it is |
|---|---|
| `incomplete frame deadline expired` | a header arrived whose payload never completed inside the 5 s frame lifetime |
| `USB transfer larger than the read buffer` | libusb `Overflow`: the device sent more in one transfer than our 64 KiB buffer, and `poll_receive` maps that to a **fatal** error |

**And the phone restarts its own session every proof timeout**: six challenges in twenty
seconds, roughly one per 3.3 s, each with a fresh nonce. That is *deliberate* —
`stalled_proofs_and_pending_approvals_have_absolute_nonrenewable_deadlines` pins that a peer
must not be able to extend its own window — so the fix for a reconnecting host is the hello
(which resets a spent session), not a longer or renewable deadline here. I tried the
opposite, the pinned test caught it, and the change was reverted.

Conclusion for this session: **G0 still passes; `G0.5` still does not complete on
hardware.** The next two things to fix are both on the host side of the reader: an Overflow
must not kill the connection (truncate, resync, or size the buffer from the endpoint's real
maximum), and the ping phase needs the same reset-and-retry treatment the exchange now has.

## Third device session: two host fixes landed, and the count still varies by size

After fixing the two reader problems found above — the read buffer is now sized by our own
1 MiB scratch instead of the reader's, so a large transfer can no longer be truncated into a
fatal `Overflow`, and an attempt that ends mid-frame now resets the reader and re-aligns
(`Usb::reset_stream`) before the retry, because a reader holding a partial header cannot
resynchronise on its own — the same session produced:

| round trips | result |
|---|---|
| 5 | FAIL — `expected authorization outcome before capabilities/media`, then after the hello retry `does not support required per-PC authorization v2` |
| 60 | **PASS** — sent 60 echoed 60, 0 mismatch, 0 timeout, 1 skipped |
| 1000 | FAIL — `deadline expired` on the first attempt, `incomplete frame deadline expired` after the hello retry |

The size dependence is the clue, and it points at the phone's session lifetime rather than at
the reader: the app rebuilds its accessory session on an absolute proof deadline (six
challenges in twenty seconds, ~3.3 s apart, fresh nonce each), so a host has to complete its
exchange inside one window. 60 round trips fit; 1000 do not.

**Next hypothesis to test, in order:**

1. **Does an *authorized* session on the phone survive?** Watch the phone's own state across a
   1000-round-trip run. If it ends, find what ends it — the host's `PING`s arriving at a
   session that has fallen back to `PROOF` (which `readMedia` feeds to the authorization
   gate, not the control path) is the first candidate, and it would explain both the
   `incomplete frame` (a frame cut mid-payload as the session dies) and the churn.
2. If the session does survive, the remaining failure is the reader's 5 s frame lifetime while
   nothing arrives — i.e. the gate's own wait policy for 1000 exchanges, not a defect.
3. Only then decide between a phone-side liveness rule and a host-side retry that survives a
   session restart mid-run; the pinned `absolute_nonrenewable` property stays either way.

## G0.5 passes at 1000 round trips (2026-10-24)

```
usb probe: 1000 round trips, 8000 ms budget each, at most 32 per second
device after the transition: 1:18d1:2d01 (accessory: true)
sent 1000 echoed 1000 sequence-mismatch 0 payload-mismatch 0 timed-out 0 skipped 1
rtt us: min 425 avg 743 p50 550 p95 1620 max 13638
PASS
```

**The blocker was the instrument, not the link.** The phone rate-limits `PING` to 64 per
second and refuses the *session* when a peer exceeds it — a deliberate protection, and the
protocol's own rule for controls on an unauthorized session. Sent at full speed (loopback-fast
USB reached ~2000 per second) the run therefore ended its own session every ~60 exchanges:
measured as *576 round trips across nine seams, 0 mismatches, 0 timeouts* — a healthy link
being killed by the probe. `--rate` now paces at 32 per second by default (half the phone's
limit, leaving room for its 1-second window), which is also why the earlier size bracket read
`5 FAIL / 60 PASS / 1000 FAIL`: 60 fit under the limit and 1000 did not.

Three fixes were needed to get here, in the order the device revealed them:

1. **Alignment at connect** (`align_stream`): the accessory endpoint holds frames from a
   previous host connection and AOA reports no disconnect, so the reader started mid-frame and
   could not complete a single frame.
2. **A spent session can be reset** (`HOST_HELLO` plus retry, and `reset_stream` between
   attempts): the phone sends one challenge per accessory session by design, so a reconnecting
   host needs a way to ask for a fresh one, and a retry from a half-read stream cannot work.
3. **Pace the round trips** (`--rate`): the phone's own rate limit is a protection, not
   friction; an instrument that ignores it measures its own violation.

RTT figures are same-clock, host to phone over USB, at a paced 32 per second. The gate forbids
a cross-device latency claim, and none is made: what is claimed is 1000 sequences matched with
the 8-byte challenge echoed every time, no malformed frame, no timeout and no disconnect.

## Verification boundary

The host-side driver and its pacing are covered by unit tests; the count above came from one
run against one XQ-GE44 on one host. Repeating it is a single command, and the phone needs a
fresh app process (`am force-stop` plus `svc usb resetUsbPort`, no reboot).

## The per-attach approval can be skipped by the user, and now says so (2026-10-24)

The dialog that appears when the phone meets the accessory has an **always allow** option.
Ticked once, Android remembers the grant for that app and that accessory, so subsequent
plugs need no tap — verified by the user on the XQ-GE44. It is cleared by reinstalling or
updating the app, which is what made it look like a per-connection cost during development
(every iteration here installed a new debug APK).

Two consequences worth keeping:

- The app asks for the permission **once per install**, not per session, so the earlier
  framing of this as inherent per-attach friction was wrong; the prompt is the *first*
  install's cost. The status line now says which box to tick.
- Our AOA identity strings are fixed (`specs/rust-host-rewrite/contracts.md`), so the
  accessory the system remembers is always the same one — a rebrand would have reset every
  user's grant.
