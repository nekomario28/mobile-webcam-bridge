## Native Xperia state before AOA

`lsusb` reported exactly one Sony candidate:

```text
Bus 001 Device 003: ID 0fce:020d Sony Ericsson Mobile Communications AB XQ-GE44
```

The USB topology reported the phone at 480 Mbit/s with no bound kernel driver on the imaging interface.

AMB direct libusb enumeration also reported:

```text
bus=1 addr=3 VID=0fce PID=020d
```

No elevated fallback was needed for enumeration (`amb_list_access=direct`).

## AOA probe

The project host probe explicitly states that ADB is not used. Against the selected Xperia:

```text
AMB G0 AOA probe; ADB is not used.
[AOA] protocol=2 on bus=1 addr=3 VID=0fce PID=020d
G0 probe passed. Re-run with --switch using the same selector.
```

This establishes that the device answered the AOA `GET_PROTOCOL` request with protocol version 2 before mutation.

## AOA transition

The same exact device selector was then used for the standard AOA identification strings and `START_ACCESSORY` transition:

```text
AMB G0 AOA probe; ADB is not used.
[AOA] protocol=2 on bus=1 addr=3 VID=0fce PID=020d
AOA START sent; waiting for USB re-enumeration...
[PASS G0] bus=1 addr=4 VID=18d1 PID=2d00
Target accessory-only PID 2d00 observed.
```

Post-transition `lsusb` independently observed:

```text
Bus 001 Device 004: ID 18d1:2d00 Google Inc. Android Open Accessory device (accessory)
```

The carrier concluded:

```text
[PASS G0 HOST] AOA accessory without ADB: 18d1:2d00
```

## Policy interpretation

For this project:

- `18d1:2d00` = accepted AOA accessory-only evidence;
- `18d1:2d01` = AOA + ADB and would fail the USB-debugging-off policy.

The observed target was `18d1:2d00`; `18d1:2d01` was not observed.

Therefore the exact supported claim is:

> The connected XQ-GE44 successfully transitioned from Sony `0fce:020d` to Android Open Accessory `18d1:2d00` using the project's libusb AOA implementation without ADB.
