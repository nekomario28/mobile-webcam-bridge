Written by the implementer. It asks for a review; it does not substitute for one. If

## What this asks for

Four areas that none of those reviews saw, plus the surfaces added since. Roughly
4 000 lines, and each area ends with a hypothesis that can be *tested*, not just read.

### A. Desktop credential storage — `host-rs/src/identity.rs` (383), `identity/store.rs`

The PC keeps a long-term key that phones pin. Questions worth asking: what happens on
Windows (DPAPI path) versus Unix (`0600` file) if the profile is copied to another
machine; whether a *restored* identity silently re-identifies as the same PC (it should
be able to, that is the point — the question is whether anything else breaks, e.g.
approvals it never earned); and whether a corrupted or truncated file is rejected
rather than half-read.

**Hypothesis to break:** replace the identity file with a *different* valid identity and
the app should present a PC the phone does not know, not resurrect approvals. If it
resurrects anything, that is a finding.

### B. Connection selection and inventory — `host-rs/src/usb.rs` (367), the inventory thread in `gui.rs`

The USB thread enumerates devices and parks; the owner chooses one. Questions: can a
device's descriptors steer a choice the user did not make; is the inventory thread's
queue bounded; does a device that disappears between enumeration and open fail closed.

**Hypothesis to break:** a device that flaps (disconnects during the AOA handshake) must
not leave the session attached to a *different* device. If the session can be steered,
that is a finding.

### C. Android manifest, backup and exported surface — `AndroidManifest.xml`, `res/xml/accessory_filter.xml`, `SessionService.kt`

Facts I read, which you should re-derive:

| Fact | Where |
|---|---|
| `allowBackup="false"` — no cloud backup of the client record or Keystore-wrapped data | `AndroidManifest.xml` |
| Only `MainActivity` is exported, for LAUNCHER and `USB_ACCESSORY_ATTACHED` | `AndroidManifest.xml` |
| No `usesCleartextTraffic`, targetSdk 35 → cleartext denied by default | manifest + `build.gradle.kts` |
| Permissions: CAMERA, INTERNET, FOREGROUND_SERVICE(_CAMERA), POST_NOTIFICATIONS. Nothing else | manifest |
| The accessory filter matches `manufacturer="Android Media Bridge"`, `model="AMB Host"` — i.e. any accessory claiming our own strings | `accessory_filter.xml` |

**Hypothesis to break:** plugging in an accessory that claims our strings opens the
app but must not start capture and must not authorise a PC. The implementer's trace
says capture needs `cameraStartRequested`, set only by the Start button or by a
quality `StartCapture` that can only follow a `Commit` accepted while
`phase == Prepared`, which is only entered when `streaming()` was already true
(`QualitySwitch.kt`, `PhoneQualityController.kt`, `MainActivity.startCamera`). Try to
reach `startCamera()` with `cameraStartRequested` false by any sequence of host frames.

### D. Outbound queues and bounded control — `transport/framing.rs`, the control channel in `session.rs`, `FramedOutbound.kt`

What bounds each queue, what a peer that stops reading does, and whether a stalled peer
can hold a lock the UI needs.

**Hypothesis to break:** a peer that stops reading must not stall the *other* direction,
and must not be able to make the host keep unbounded memory. If either is possible, it
is a finding.

## What a finding should look like

Same shape as the existing reviews: an ID, severity, the file and line, the sequence
that produces the bad state, what was observed versus what was argued, and an evidence
boundary ("measured on loopback", "static only", "needs device"). A finding that cannot
name its reproduction is a question, and questions are welcome as such.

## The one instruction

Attack the **Evidence** column of `security-coverage.md`. This repository has twice
had a test that passed for the wrong reason — a capture gate that accepted a deleted
fixture, and a visibility rule that a second writer overruled without failing anything.
A claim whose test is green for the wrong reason is worth more than a new bug.
