## What this asks for

Five areas, each ending with a hypothesis that can be *tested* rather than argued. The first is the
one worth your time: it is new instrumentation whose verdicts are now load-bearing claims about the

### A. The two device instruments, and the claims they now carry

Files: `android/app/src/androidTest/java/dev/nekomario/amb/UsbReaderReleaseMeasurement.kt`,
`.../UsbFrameOwnerMeasurement.kt`, `.../UsbPermissionInstrumentation.kt` (the four opt-ins that
reach them), `host-rs/tools/send-hello.py` (the host half), and the two evidence documents
`docs/evidence/2026-10-25-usb-reader-release.md` and `2026-10-25-usb-frame-owner.md`, which quote
the raw runs.

Facts I read or produced, all of which you should re-derive:

| Claim | Where it comes from |
|---|---|
| Closing the accessory descriptor returns a blocked read in 0 ms, 10/10 raw and 10/10 for a real session, with "the read was blocked" asserted on every iteration | reader-release evidence, logcat quoted there |
| The platform's message is `InterruptedIOException: read interrupted by close() on another thread` | same |
| With one reader blocked, the host's 24-byte `HOST_HELLO` completes and that session ends with `PC authorization proof rejected`; with the endpoint idle, iterations end only by their own absolute 5 s proof deadline | frame-owner evidence, plus the host script's output |
| Two `openAccessory` calls both succeed; the second reader's first read fails with `EIO` | reader-release evidence |
| The accessory interface is `class 0xff / subclass 0xff` with host→phone `0x01` and phone→host `0x81` | `host-rs/src/usb.rs`'s endpoint selection, and the host script's own print |

**Hypothesis A1 — the frame-owner verdict could be produced by anything already in the endpoint.**
AOA reports no disconnect, so the endpoint holds whatever a previous host left there, and the
instrument arms a *fresh* session per iteration. If a frame from an earlier write can be consumed by
a later iteration, `PC authorization proof rejected` can appear without the host's measured write.
Try to produce it with the host writing nothing. The run's own defence is that the host script
printed its drain before writing (one `0x0a` challenge, no frames) — re-derive that, do not trust it.

**Hypothesis A2 — the release measurement may show the JVM abandoning a read rather than the
endpoint being released.** The intercepted `read` is a libcore/JVM one, and its message names
`close()` on another thread. The kernel's URB for that endpoint could still be pending, which is
exactly the case where a *second* reader would be refused — and the same document measures `EIO` for
a second reader. Separate the two: find whether a released reader leaves the endpoint immediately
usable, or whether "released" is only true from the JVM's side.

**Hypothesis A3 — the control is weaker than it reads.** The idle-endpoint iterations end by their
own proof deadline, which is presented as proof that an idle endpoint delivers nothing. That is a
5 s window inside one process: try to make a session end *earlier* than its deadline on an idle
endpoint (a stale byte, a leftover from a previous run, a rate limit reached by the instrument's own
retries), because any of those would make the control's silence mean less.

### B. The two rules that replaced the false-green tests

Files: `android/app/src/main/java/dev/nekomario/amb/StopAction.kt`, `.../ReaderHandover.kt`, the
`MainActivity` diff in the same commits, `android/app/src/test/.../{StopActionTest,ReaderHandoverTest,SessionServiceWiringTest,SecondarySurfaceWiringTest}.kt`.

The review's WR2/WR3 complaint was that substring assertions on source text stay green while the
behaviour is absent. Each rule now has an owner with behaviour tests, and the wiring test asserts
only that the Activity *delegates* to it. That leaves a delegation-shaped hole one level up.

**Hypothesis B1 — a path to an ungated send still exists.** `sendPairingInfo` and `updateCapabilities`
are gated on `permitted()` inside `AuthorizedMediaSession`, and the Activity is pinned as calling
`StopAction.accepts`. Find a second caller, a second implementation of `MediaSession`, or a route
(the service, the notification, a test-only fixture that ships in the wrong variant) that reaches
the wire without that gate — which would leave every test green.

**Hypothesis B2 — the stop credential can be bypassed by something other than the token.**
`StopAction` compares an unguessable per-process value. Look for another way to end a live session
from outside the process that does not need it (the service, an exported surface, the accessory
intents the manifest declares).

### C. The answer to the review's Q1, and the code it justified

Files: `host-rs/src/usb.rs` (`align_stream`, `Usb::connect`, `reset_stream`), `host-rs/src/wire.rs`
(the header rejection), `host-rs/src/video.rs` (the retry), `host-rs/src/usb_probe.rs` (the reset and
its warning). The disposition in `independent-review-2026-10-24.md` argues that a wrong alignment
verdict cannot produce a *silently wrong* frame because the reader rejects a header that does not
begin `AMB1`, and that the silence verdict is deliberate (an app that has not started sending is
silent too).

**Hypothesis C1 — a misaligned stream can still parse.** The claim rests on a 4-byte magic. Find a
state where a tail or a coalesced transfer begins with `AMB1` and a plausible length, so that the
reader accepts a frame that is not the frame the phone sent. `host-rs/tests/parsers.rs` and
`host-rs/fuzz/` are the tools; the endpoint's coalescing behaviour is documented in `docs/gates.md`
G0.5.

**Hypothesis C2 — the new trace line is a claim about behaviour that the code does not have.** The
commit that added `usb trace: align_stream verdict=…` says the verdict changes nothing
behaviourally. Verify that, rather than reading it: make the verdict false by construction and check
that the only difference is a line on stderr.

### D. The coverage rows the last review asked for

Files: `docs/reviews/security-coverage.md` (the `HOST_HELLO`, rate-limit, handover and probe rows)
against `android/app/src/main/java/dev/nekomario/amb/SessionControl.kt`,
`android/.../PhoneAuthorization.kt`, `android/.../AccessorySession.kt`, `host-rs/src/usb_probe.rs`,
`host-rs/src/usb.rs`.

**Hypothesis D1 — the rate-limit row overstates its bound.** It says PING, `HOST_HELLO` and IDR
requests are limited per *anchored* one-second window, and that an overrun is an error for PING and
a drop for the other two. Drive the window boundary and try to get more than the stated maximum
through, or to get a drop that should have been an error (or the reverse).

**Hypothesis D2 — the handover row's device half is still thinner than the row implies.** It claims
"two accessory readers never share one endpoint" and now cites a measured release and a measured
`EIO`. Try to construct the state the guard prevents *without* the guard: two descriptors, the
first reader blocked, the second refused — and show what the guard's absence would actually change
on the wire, because the row currently claims the consequence rather than showing it.

### E. Documentation that is now load-bearing

Files: `docs/gates.md` (G0's preconditions, the local text and host gate runbooks, the device
instrument section), `CONTRIBUTING.md` (Before you start).

**Hypothesis E1 — "USB debugging does not have to be off" is true only when adb is idle.** The
claim comes from one day's measurements where adb held its own interface and the host claimed the
accessory. Push bytes over adb (a large `adb push`, or a logcat stream) while the accessory session
runs, and see whether the host's claim, or its transfers, degrade.

## What a finding should look like

The same shape as the existing reviews: an ID, severity, the file and line, the sequence that
produces the bad state, what was observed versus what was argued, and an evidence boundary
("measured on loopback", "static only", "needs device"). A finding that cannot name its reproduction
is a question, and questions are welcome as such.

## The one instruction

Attack the **verdicts of the new instruments** before anything else. This repository has three times
had a result that looked like evidence and was not: a release measurement that printed
`released=true in 0 ms` twenty times without ever establishing that the read was blocked, a
frame-owner verdict that counted the reader's own proof deadline as a consumed frame, and a
diagnosis that blamed the environment for holding an interface it had simply claimed wrongly. All
three were found by the implementer, after the fact. A fourth would cost the next reader of these
documents the same trust.
